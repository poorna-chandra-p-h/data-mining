Section B, Part (d): Database Schema and Access PathTo ensure the LSH lookup structure survives a process restart and is queryable as relational data, I designed an Inverted Index schema directly inside DuckDB.Schema Design:The permanent lookup structure is defined as:CREATE TABLE lsh_index (band_id INTEGER, band_hash VARCHAR, notice_id VARCHAR)When a new notice is processed, its 20 MinHash bands are generated and inserted into a temporary table (new_notice), which is then joined against the persistent lsh_index.Access Path Selection & Justification:Adopted Method: Equi-Join resulting in a Hash Join. By using explicit equality conditions (=), the DuckDB query planner is instructed to build a tiny, in-memory hash table of the incoming notice's 20 bands. It then scans the massive lsh_index exactly once, probing the hash table in $O(N)$ time.Rejected Method: Nested Loop Join. If the database were forced to evaluate non-equi conditions or lacked memory, it would fall back to a nested loop. This path takes the first band of the new notice and scans the entire index, then takes the second band and scans the entire index again, yielding an intractable $O(N \times M)$ complexity that would destroy the 20-minute nightly budget.Measurements:I simulated a corpus of 500,000 index rows and evaluated the physical query plans. EXPLAIN ANALYZE confirmed the query planner explicitly selected the HASH_JOIN node for the equi-join, which physically located the rows and completed the cross-reference in 0.0057 seconds of wall-clock time.
